# 機台（app.html）↔ 活動（events.html）關聯設計備忘

**狀態：** 設計定案，尚未動手改 `docs/spec.md` 或程式碼
**日期：** 2026/09/04

---

## 一、現況

`app.html`（機台）跟 `events.html`（活動）讀同一份 Google Sheet 的兩個獨立分頁，彼此完全沒有關聯欄位。`main.js` 跟 `events.js` 也是各自獨立、互不 import，延續專案「各檔案自帶所需邏輯」的慣例。

## 二、關聯鍵：不新增欄位，靠標題＋期間比對

跟 Gill 確認過：如果機台屬於某檔活動，機台分頁 **C 欄（店名）** 一定會直接填該活動的名稱，所以可以沿用活動分頁現有的分組邏輯——「標題＋期間」字串比對（`events.js` 的 `getGroupKey()` / `groupKeyMap`）——來判斷某台機台屬不屬於某檔活動。不新增 Google Sheet 欄位。

### 卡住的地方：活動分組是「同標題同期間」，但不是每個地點都有相同機台

活動分頁一列＝一個地點，`events.js` 會把同標題＋同期間的多列合併成一組（`group.locations[]`），例如同一檔快閃店在台北、台中、高雄三地開。但**同一組裡不同地點擺的機台不一定一樣**——不能「配對到活動群組」就把該群組底下全部機台都列出來，一定要再細分到「這台機台對應哪一個地點」。

**解法：兩段比對**

1. **群組比對**：機台的「店名＋期間限定」對到活動的「標題＋期間」→ 找到對應的活動群組（沿用 `events.js` 現有的 `getGroupKey()` 正規化邏輯，機台端也要用同一套正規化規則，避免全形/半形、空白差異導致比對失敗）。
2. **地點比對**：在該群組的 `locations[]` 裡，找出跟這台機台同一個地點的那一列。比對優先順序建議：
   - 先比**縣市**（機台 F 欄 vs 地點 F 欄）完全一致；
   - 同縣市有多個地點時，再比**場地**（機台 E 欄 vs 地點 E 欄）是否有子字串相符；
   - 都比不出來就用經緯度算最近距離（`haversineKm()`，`grid.js`/`events.js` 都已有現成函式）取最近的一筆。
   - 三段都比不出來 → 視為「找不到對應地點」，這台機台不顯示活動標籤（寧可不標，不要標錯）。

這個比對邏輯建議寫成共用的小工具函式，兩邊各自複製一份（延續專案慣例），或者評估要不要例外抽成共用檔案——這點之後動手時再一起決定。

## 三、畫面呈現

### app.html（機台端）：列表卡片、地圖 popup、機台詳情都要顯示

因為列表卡片跟地圖 popup 版面窄，用小標籤而非整行文字：

- **列表/地圖卡片**：類型徽章（抽卡機/相卡機）旁邊加一個小型可點擊 chip，例如「🎪 期間活動」，用活動分類色碼（`EVENT_CATEGORIES`）當邊框色，跟 events.html 視覺語言一致。空間有限，先不放活動全名。
- **機台詳情 Modal**：完整顯示，例如「🎪 期間活動：《鏈鋸人快閃店》→」，點擊跳去 events.html 並定位到對應活動＋地點（見下方「待實作」）。

技術上，`main.js` 目前已經會 fetch 活動分頁 CSV（v32.1 起，為了比較最後更新時間戳），可以擴充這次 fetch 順便解析活動標題／期間／地點欄位，不用多一次 request。

### events.html（活動端）：詳情 Modal 內、依「目前選中的地點」顯示

活動詳情 Modal 已經有多地點時的「城市分頁」切換 UI（`events-city-tab` / `locationSectionHtml()`）。相關機台清單要放在這個地點區塊裡面、跟著分頁一起切換，**不要**放在群組層級——因為機台是綁地點,不是綁整檔活動。

- 每個地點分頁底下加一個「相關機台（N）」小區塊，列出該地點對應的機台（縮圖＋名稱＋類型），點擊用機台既有的 `?id=<永久ID>` 分享連結機制跳回 app.html 開啟該機台詳情（這條路徑已存在，不用新做）。
- 沒有比對到任何機台的地點：這區塊不顯示，不用放「無機台」之類的空狀態文字。

### 月曆橫幅／拼貼卡片：這輪不加標示

活動列表層級的卡片（月曆橫幅、拼貼卡片）先不加「有機台」的提示圖示，避免版面更擠，MVP 先集中在詳情層級。之後如果有需要再評估。

## 四、待實作項目（下次動手時要一起做的）

1. `docs/spec.md` 補上這套比對邏輯的說明（機台/活動欄位規格章節都要提到，這是文件明確禁止未經指示更動的檔案之一，需等 Gill 下指令）。
2. `main.js` 擴充活動 CSV 解析，算出每台機台對應的活動＋地點（沒對到就不算）。
3. `events.js` 的 `locationSectionHtml()` 加相關機台區塊，並實作 `?event=` 網址還原邏輯（spec 裡標記「尚未實作」，這次可以順便補上，讓機台端的連結有地方可以跳回去）。
4. app.html 卡片／popup／詳情三處的活動標籤 UI 與樣式（`style.css`）。
5. 決定機台↔活動比對函式要各自複製一份，還是抽成共用邏輯。

## 五、還沒拍板、下次動手前建議先想清楚的細節

- 標題正規化規則要多寬鬆？（全半形空白、括號、標點要不要忽略比對）
- 機台的「店名」欄位如果只是「巧合」跟某活動同名同期間，但其實無關（機率低但不是零），要不要留一個「不要顯示活動標籤」的手動排除機制？目前設計是純自動比對，沒有人工覆寫的退路。
- app.html 標籤點擊跳轉 events.html 時，如果活動已經下架/找不到，fallback 行為要跟機台分享連結的「三段式判斷」（永久ID精準比對／退回不顯示／toast提示）一致，還是簡化處理？
